### YELLOW FP-03: Extended Command Detection Relies on Keyword Matching

**Location:** sf-pm.md lines 298-337 (brainstorm), 343-388 (UX)
**Context:** PM decides whether to invoke /sf:brainstorm or /sf:ux based on signals in user request
**Friction:** The trigger detection is heuristic-based (keyword matching: "brainstorm", "ideas", "explore" for brainstorm; "interface", "UI", "dashboard" for UX). Users may not use these keywords even when the features would help.
**Evidence:** From sf-pm.md lines 300-305:
```markdown
**Uncertainty Signals:**
- Request is vague or ambiguous ("I want something like...", "maybe we could...")
- User signals uncertainty ("I'm not sure what I want", "let me think")
```
These signals require natural language interpretation, not just keyword matching. A user saying "build a settings page" doesn't use UX keywords but would benefit from /sf:ux.

**Impact:** UX and brainstorm may be under-invoked for features that would benefit. Over-reliance on explicit keywords misses implicit needs.
**Category:** Under-specification
**Recommendation:** Add scope-based defaults (e.g., medium+ scope with UI components auto-suggests UX). Consider LLM-based intent detection rather than pure keyword matching.

### YELLOW FP-04: Scope Approval Gate Threshold May Cause User Fatigue

**Location:** sf-pm.md lines 174-179
**Context:** PM determines when to engage user for scope approval
**Friction:** The threshold is binary: trivial/small = auto-approve, medium+ = user confirmation. This works well initially but may cause fatigue for experienced users who trust the system.
**Evidence:** From sf-pm.md lines 174-179:
```markdown
| Condition | Action |
|-----------|--------|
| scope < medium | Auto-approve, continue |
| scope >= medium | **Engage user** for confirmation |
```
Every medium feature requires user confirmation, even if the user has confirmed similar scopes before.

**Impact:** Experienced users may find repeated confirmations tedious. No "trust escalation" for users who consistently approve.
**Category:** Over-specification
**Recommendation:** Consider adding a "fast track" mode or user preference for auto-approving certain scope levels. Track approval history to suggest fast-tracking.

### YELLOW FP-05: Agent State Initialization is Manual and Error-Prone

**Location:** sf-pm.md lines 539-568
**Context:** PM initializes Agent States table in STATE.md after triage
**Friction:** The initialization requires PM to read 0-triage.md, extract the agent sequence, then manually construct the Agent States table. This is procedural and depends on PM correctly parsing the sequence.
**Evidence:** From sf-pm.md lines 546-567:
```markdown
1. Read `0-triage.md` to get the agent sequence
2. Create the Agent States section in STATE.md with all agents from the sequence:

```markdown
## Agent States

| Agent | State | Blocker | Since |
|-------|-------|---------|-------|
| analyst | pending | - | {iso-timestamp} |
...
```

Only include agents that are in the triage sequence.
```
The instruction "Only include agents that are in the triage sequence" requires PM to conditionally exclude agents, adding cognitive load.

**Impact:** If PM misses an agent or includes an extra one, STATE.md becomes inaccurate. Downstream routing may fail.
**Category:** State Confusion
**Recommendation:** Generate Agent States table automatically from pillar selection. The mapping is deterministic: pillars -> agent sequence -> state table.

### RED FP-06: Synthesis Gate Lock Approval Duplicates Scope Approval

**Location:** sf-pm.md lines 1203-1212
**Context:** PM presents 5-requirements-lock.md for user approval (for medium+ scope)
**Friction:** Users approve scope at the scope gate, then approve the lock at synthesis. Both gates require user interaction for medium+ features. The lock approval feels redundant if scope was already approved and all pillar agents executed correctly.
**Evidence:** From sf-pm.md lines 1203-1212:
```markdown
| Scope | Approval Required |
|-------|-------------------|
| trivial | No - PM auto-approves |
| small | No - PM auto-approves |
| medium | Yes - user approval |
| large | Yes - user approval |
| complex | Yes - user approval |
```
This is identical to the scope approval threshold. A medium feature requires:
1. User confirms scope (gate 1)
2. User approves lock (gate 2)

Two approvals for the same feature before any code is written.

**Impact:** User friction. Two similar approval prompts may lead to rubber-stamping the second one, reducing its value.
**Category:** Over-specification
**Recommendation:** Consider combining gates for medium scope: approve scope + pillar outline together. Large/complex can retain separate lock approval due to higher complexity. Or: auto-approve lock if scope was user-approved and no conflicts detected during synthesis.

### YELLOW FP-07: COMMS Resolution Has No Timeout or Escalation Path

**Location:** sf-pm.md lines 574-603
**Context:** PM routes COMMS between agents and waits for resolution
**Friction:** The COMMS protocol waits indefinitely for resolution. If a target agent is slow or fails to respond, there's no timeout. The only escalation is "If same agents have exchanged COMMS twice without resolution" -> CONFLICTS.md.
**Evidence:** From sf-pm.md lines 598-602:
```markdown
**4. Check for unresolved exchanges:**

If same agents have exchanged COMMS twice without resolution (A->B->A->B):
1. Create CONFLICTS.md entry (see Conflict Resolution)
2. Do NOT continue routing - PM must resolve conflict first
```
No mention of timeout. If Agent B never responds, workflow halts.

**Impact:** Workflow can hang if COMMS is never resolved. No graceful degradation.
**Category:** Loop Escape
**Recommendation:** Add timeout (e.g., 24h for async workflows, 5min for synchronous). After timeout, escalate to PM decision or user intervention.

### YELLOW FP-08: Drift Correction Routing Doesn't Consider Fix Complexity

**Location:** sf-pm.md lines 1536-1690
**Context:** PM writes correction file and re-invokes agent after MAJOR_DRIFT
**Friction:** The correction file format is standardized, but the routing decision (re-invoke vs escalate) only considers iteration count, not fix complexity. A simple typo fix and a major architectural change both get the same 2-retry limit.
**Evidence:** From sf-pm.md lines 1649-1657:
```markdown
IF dev_iterations <= 2 AND agent == dev:
  Invoke /sf:dev (Dev will detect correction file, enter DRIFT_FIX mode)

IF iterations > 2:
  Escalate to user
```
No consideration of whether the drift is a minor gap or a fundamental misunderstanding.

**Impact:** Simple fixes may escalate unnecessarily if they happened to be drift iteration #3. Complex issues may retry too many times before escalating.
**Category:** Under-specification
**Recommendation:** Consider drift severity in retry logic: MINOR_DRIFT issues get more retries; MAJOR_DRIFT with fundamental gaps escalate faster. Add "fix complexity estimate" to correction file.

### RED FP-09: QA Drift Classification Lacks Clear Heuristics

**Location:** sf-pm.md lines 1586-1628
**Context:** PM classifies QA drift as TEST_DRIFT or CODE_ISSUE to route to correct agent
**Friction:** The classification relies on PM analyzing test results and asking "Does the test correctly reflect the AC?" This requires semantic understanding of both the test and the AC. The signals provided are high-level.
**Evidence:** From sf-pm.md lines 1600-1610:
```markdown
**Classification Process:**

1. Read `7-qa-output.md` test results
2. For each failing/missing test, ask:
   - Does the test correctly reflect the AC from requirements lock?
   - If yes -> CODE_ISSUE (code wrong)
   - If no -> TEST_DRIFT (test wrong)
```
This is a judgment call requiring deep analysis. No clear heuristics like "if test file was not modified, likely CODE_ISSUE."

**Impact:** Misclassification routes to wrong agent, wasting an iteration. Correct classification requires significant cognitive effort.
**Category:** Handoff Ambiguity
**Recommendation:** Add file-based heuristics: if test file unchanged since QA wrote it -> likely CODE_ISSUE. If implementation matches AC but test asserts wrong value -> likely TEST_DRIFT. Provide examples in the protocol.

### YELLOW FP-10: Report Generation Triggers Are Disconnected from Workflow

**Location:** sf-pm.md lines 1819-1878
**Context:** PM detects report-related requests and spawns skill-detector
**Friction:** Report triggers ("status report", "health check", "risk assessment") are detected via phrase matching, separate from the main feature workflow. A user mid-workflow who asks "how's it going?" triggers health check instead of status update on the feature.
**Evidence:** From sf-pm.md lines 1825-1831:
```markdown
| User Says | Detected Intent |
|-----------|-----------------|
| "health check", "how's it going" | Health Assessment |
```
"How's it going?" is ambiguous - could be a greeting, could be asking about feature progress, could be requesting formal health check.

**Impact:** False positive report triggers interrupt workflow. User intent misinterpreted.
**Category:** Over-specification
**Recommendation:** Add context awareness: if feature in progress, interpret "how's it going?" as status inquiry, not health check skill invocation. Require more explicit triggers for formal reports ("generate health report" vs "how's it going").
