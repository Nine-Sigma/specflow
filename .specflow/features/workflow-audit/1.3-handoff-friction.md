### YELLOW FP-23: Analyst Outputs Two Files Without Clear Handoff Point

**Location:** sf-analyst.md (implicit), 1-workflow-map.md
**Context:** Analyst produces 0-scope.md, then 1.5-codebase-constraints.md, then 1-spec.md
**Friction:** Analyst has multiple output points with PM reviews between them. The handoff timing is unclear: does PM review 0-scope.md before codebase analysis, or wait for all outputs?
**Evidence:** From 1-workflow-map.md lines 289-305:
```markdown
### Phase: Codebase Analysis (Analyst)
| Entry Point | PM approves scope |

### Phase: Spec Creation (Analyst)
| Entry Point | PM routes after codebase analysis |
```
Three separate phases (Scope Assessment, Codebase Analysis, Spec Creation) all involving Analyst, with PM gates between. But the workflow map shows Analyst -> PM -> Analyst -> PM -> Analyst flow.

**Impact:** PM must track Analyst's multi-stage progress. More handoff points = more opportunities for state confusion.
**Category:** Handoff Ambiguity
**Recommendation:** Consider consolidating Analyst's work into fewer handoff points. Option A: Analyst completes all three in one invocation, PM reviews once. Option B: Keep gates but document clear state transitions.

### YELLOW FP-24: COMMS Protocol Creates Cross-Agent Coupling

**Location:** sf-dev.md lines 147-214, sf-qa.md lines 200-266
**Context:** Agents can send COMMS to request information from other agents
**Friction:** COMMS creates a "blocking" state where the sender cannot proceed. The protocol requires PM to route the question and re-invoke the blocked agent. This creates tight coupling between agents through PM.
**Evidence:** From sf-dev.md lines 193-214:
```markdown
4. Mark yourself BLOCKED:
   - Update `.specflow/STATE.md`:
     - Change agent state row for `dev` to `blocked`
     - Set blocker to your COMMS filename

5. Append to PROGRESS.md:
   ...
   Awaiting {target} response. Returning control to PM.

6. **STOP** - Do not continue work while blocked
   - Return control to PM
   - PM will route your question and reinvoke you after response
```
The COMMS sender halts completely. No partial work. PM becomes the message router.

**Impact:** If COMMS are frequent, PM becomes a bottleneck. Workflow serializes unnecessarily.
**Category:** Over-specification
**Recommendation:** Consider async COMMS: agent notes question, continues with assumption, flags assumption for review. PM resolves if assumption was wrong. Reduces blocking.

### YELLOW FP-26: File Numbering Has Gaps and Optional Files

**Location:** 1-workflow-map.md lines 594-612
**Context:** Standard file numbering convention (0-triage, 1-spec, 2-architecture, etc.)
**Friction:** Some numbers are overloaded (5-test-plan.md AND 5-requirements-lock.md AND 5-qa-tests.md all use "5"). Some are optional (3-security, 4-cost). This creates confusion about what exists.
**Evidence:** From 1-workflow-map.md lines 594-612:
```markdown
| Number | File | Created By |
|--------|------|------------|
| 5 | 5-test-plan.md | TEA |
| 5 | 5-requirements-lock.md | PM |
| 5 | 5-qa-tests.md | QA (qa-first only) |
```
Three files with the same number prefix. Also:
```markdown
| 3 | 3-security.md | Security (optional) |
| 4 | 4-cost.md | Cost (optional) |
```
If security pillar is skipped, there's a gap from 2 to 5.

**Impact:** Agents cannot assume file existence by number. Must check for each file. Naming is inconsistent.
**Category:** State Confusion
**Recommendation:** Options: (1) Use phase-based naming (spec-phase/1-scope.md, design-phase/2-arch.md) or (2) Use descriptive names without numbers (scope.md, spec.md, architecture.md). Current hybrid approach has ambiguity.

### YELLOW FP-27: Agent States Table Update is Manual and Distributed

**Location:** agent-pattern.md lines 45-52, sf-dev.md lines 259-263
**Context:** Each agent updates STATE.md after execution
**Friction:** Every agent is responsible for updating STATE.md manually. If an agent fails to update (or updates incorrectly), state tracking breaks.
**Evidence:** From sf-dev.md lines 259-263:
```markdown
3. Update `.specflow/STATE.md`:
   - last-agent: dev
   - next-agent: pm
   - phase: checkpoint
   - dev_iterations: {N} (if DRIFT_FIX_MODE, increment; else keep current)
```
From agent-pattern.md lines 45-52:
```markdown
5. WRITE OUTPUT
   |- Write to .specflow/features/{slug}/{N}-{type}.md
   |- Append to PROGRESS.md
   |- Update STATE.md (last-agent, next-agent: pm)
```
Multiple steps, multiple files, manual updates.

**Impact:** Inconsistent state if agent fails mid-output. No transactional guarantees.
**Category:** State Confusion
**Recommendation:** Consider automated state updates: PM validates agent completion and updates state. Single authority for state changes reduces inconsistency.

### RED FP-28: Context Loss at PM Synthesis Gate

**Location:** sf-pm.md lines 1107-1201
**Context:** PM synthesizes multiple pillar outputs into requirements lock
**Friction:** PM creates the requirements lock by extracting and combining sections from multiple files. This is a compression operation - some context is lost. Architect decisions may not fully transfer.
**Evidence:** From 1-workflow-map.md lines 388-402:
```markdown
**Entry Point:** TEA completes
**Inputs:**
- 1-spec.md (FR, AC from Analyst)
- 1.5-codebase-constraints.md (TC, IP from Analyst)
- 2-architecture.md (TC from Architect)
- 3-security.md (SC from Security)
- 4-cost.md (cost constraints)
- 5-test-plan.md (test specifications from TEA)
```
Six input files compressed to one output file. Rationale and context from ADRs may not transfer.

From add-password-reset/PROGRESS.md, Architect made decisions like:
```
- Token entropy: 256 bits (exceeds OWASP 128-bit minimum)
- Password hashing: Argon2id (OWASP recommended)
```
Are these in the requirements lock, or lost?

**Impact:** Dev may not understand WHY a constraint exists. May implement correctly but without understanding, leading to maintenance issues.
**Category:** Context Loss
**Recommendation:** Requirements lock should include brief rationale for key constraints. Add "Rationale" column to TC/SC tables. Or: keep ADR references in lock so Dev can read full context if needed.
