### GREEN FP-11: Dev Mode Detection Priority Chain is Clear

**Location:** sf-dev.md lines 17-45
**Context:** Dev agent determines execution mode on invocation
**What Works Well:** The priority chain (DRIFT_FIX_MODE > FIX_MODE > STANDARD_MODE) is explicit and testable. Each mode has concrete detection criteria.
**Evidence:** From sf-dev.md lines 21-44:
```markdown
**Priority 1: Check for Drift Correction Mode**
```bash
ls .specflow/features/{slug}/drift/correction-dev-*.md 2>/dev/null
```
IF correction files exist:
  mode = DRIFT_FIX_MODE

**Priority 2: Check for Review Fix Mode**
IF context contains "Fix Request from Review":
  mode = FIX_MODE

**Default: Standard Mode**
ELSE:
  mode = STANDARD_MODE
```
The detection is file-based (drift) or context-based (fix request), not ambiguous heuristics.

**Impact:** Dev reliably enters the correct mode. No mode confusion.
**Category:** N/A (working well)
**Recommendation:** Preserve priority-based mode detection. Consider adding debug logging for mode selection.

### YELLOW FP-14: Dev Drift Fix Versioning Scheme is Confusing

**Location:** sf-dev.md lines 92-94
**Context:** Dev outputs versioned files in DRIFT_FIX_MODE
**Friction:** The versioning scheme "Version = previous version + 1 (or 2 if first fix)" is non-intuitive. Why start at v2? This creates off-by-one confusion.
**Evidence:** From sf-dev.md lines 92-94:
```markdown
**Output versioning:**
- DRIFT_FIX iteration 1 -> write `6-dev-output-v2.md`
- DRIFT_FIX iteration 2 -> write `6-dev-output-v3.md`
- Version = previous version + 1 (or 2 if first fix)
```
First standard output is `6-dev-output.md` (no version), first drift fix is `v2`. Why not `v1`?

**Impact:** Developers reading the files may miscount iterations. File naming is inconsistent (no version vs v2+).
**Category:** State Confusion
**Recommendation:** Either version all files (v1, v2, v3...) or clarify that no-version = v1 in documentation. Consistent naming reduces confusion.

### YELLOW FP-16: Review VERIFY_FIXES Mode Scope Restriction is Aspirational

**Location:** sf-review.md lines 319-409
**Context:** Re-review only checks specific findings from previous iteration
**Friction:** The scope restriction "Do NOT look for new issues" relies on skill behavior, not enforcement. Skills could still report new findings.
**Evidence:** From sf-review.md lines 375-377:
```markdown
## Scope Restrictions

- ONLY verify the findings listed above
- Do NOT look for new issues
- Do NOT review files outside the fix scope
- EXCEPTION: If you discover a new CRITICAL issue while verifying, report it
```
The "EXCEPTION" clause contradicts the restriction. Skills can report "NEW_CRITICAL_DISCOVERED" which is... looking for new issues.

**Impact:** VERIFY_FIXES mode is not strictly enforced. May cause scope creep in re-reviews.
**Category:** Over-specification
**Recommendation:** Either remove CRITICAL exception (pure verification) or rename mode to "VERIFY_FIXES_WITH_CRITICAL_DETECTION" to be honest about scope. Current wording is contradictory.

### RED FP-17: Drift vs Bug Classification at QA Checkpoint Has No Automated Heuristics

**Location:** sf-review.md lines 1256-1267
**Context:** Distinguishing between drift (spec mismatch) and bugs (code errors) at QA checkpoint
**Friction:** The classification process described in sf-review.md requires semantic judgment. No automated signals are provided.
**Evidence:** From sf-review.md lines 1256-1267:
```markdown
### Drift vs Test Failure

| Situation | Type | Owner | Resolution |
|-----------|------|-------|------------|
| "Dev built logout but spec says password reset" | Drift | PM | Re-route to Dev |
| "Logout test fails: expected 200, got 401" | Bug | Review | Fix loop to Dev |
| "QA tests don't cover AC-03" | Drift | PM | Route to QA |
```
The examples require understanding intent vs implementation. No file-based or signal-based heuristics.

**Impact:** Misclassification routes to wrong agent (PM vs Review). Wastes iteration. This is the same issue as FP-09 from PM triage, but manifests in Review.
**Category:** Handoff Ambiguity
**Recommendation:** Add automated heuristics:
- Test file unchanged since QA wrote it + test fails -> likely CODE_ISSUE
- Test asserts different value than AC specifies -> likely TEST_DRIFT
- Implemented endpoint returns unexpected status -> likely BUG
- Implemented endpoint does wrong action -> likely DRIFT

### YELLOW FP-18: Parallel vs Sequential Fix Routing Depends on "Independence"

**Location:** sf-review.md lines 524-533
**Context:** Review decides whether to route Dev and QA fixes in parallel or sequentially
**Friction:** "Independence check" relies on Review's judgment: "Can be fixed without affecting other findings." No concrete criteria provided.
**Evidence:** From sf-review.md lines 524-533:
```markdown
**Independence check:**
- "Independent? Yes" = Can be fixed without affecting other findings
- "Independent? No" = Fix may impact other findings (e.g., refactor affects tests)

**Parallel routing decision:**
```
IF all_dev_issues_independent AND all_qa_issues_independent:
    route_parallel = true
ELSE:
    route_parallel = false
    note_dependencies = [list of dependent pairs]
```
```
How does Review determine if a naming change "affects" a test? Requires analysis.

**Impact:** Conservative routing (sequential) wastes time. Aggressive routing (parallel) causes merge conflicts.
**Category:** Under-specification
**Recommendation:** Add heuristics for independence:
- Same file touched by both -> NOT independent
- Test file + source file -> typically independent (parallel OK)
- Refactor finding + any other finding -> NOT independent
- Default to sequential if unsure (safe but slower)

**Location:** sf-dev.md lines 61-67
**Context:** Dev in FIX_MODE should only fix specific findings
**Friction:** The scope enforcement is a list of "Do NOT" instructions. No automated enforcement.
**Evidence:** From sf-dev.md lines 61-67:
```markdown
**SCOPE ENFORCEMENT:**
Do NOT:
- Add new features
- Refactor unrelated code
- Exceed scope of fix request
- Change architecture without escalation
```
This relies on Dev (the agent) following instructions. No validation step.

**Impact:** Dev may fix more than requested, causing scope creep. Extra changes may introduce new bugs.
**Category:** Under-specification
**Recommendation:** Add validation in Review: compare files changed in fix to files listed in fix request. Flag unexpected file changes.

### YELLOW FP-20: Test Skill Re-Run in VERIFY_FIXES Has Regression Discovery Ambiguity

**Location:** sf-review.md lines 997-1011
**Context:** Test skills may discover new failures during verification
**Friction:** The handling of "NEW_CRITICAL_DISCOVERED" during verification is unclear. Is it added to this iteration's findings? Does it reset the iteration count?
**Evidence:** From sf-review.md lines 1005-1011:
```markdown
Handle as:
```
IF test skill reports NEW_CRITICAL_DISCOVERED:
    Add to findings as NEW_CRITICAL
    Status = NEEDS_FIXES (not ESCALATED on first occurrence)
    Note: "Regression discovered during verification"
```
```
"First occurrence" of what? First discovery ever, or first in this feature? If regression keeps happening, when does escalation occur?

**Impact:** Regressions may delay feature indefinitely. No clear escalation path for repeated regressions.
**Category:** Loop Escape
**Recommendation:** Track regression discoveries separately. After N regressions (suggest 2), escalate regardless of iteration count. A feature that keeps regressing needs architectural review.
