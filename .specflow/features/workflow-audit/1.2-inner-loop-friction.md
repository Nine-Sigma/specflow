### YELLOW FP-14: Dev Drift Fix Versioning Scheme is Confusing

**Location:** sf-dev.md lines 92-94
**Context:** Dev outputs versioned files in DRIFT_FIX_MODE
**Friction:** The versioning scheme "Version = previous version + 1 (or 2 if first fix)" is non-intuitive. Why start at v2? This creates off-by-one confusion.
**Evidence:** From sf-dev.md lines 92-94:
```markdown
**Output versioning:**
- DRIFT_FIX iteration 1 -> write `6-dev-output-v2.md`
- DRIFT_FIX iteration 2 -> write `6-dev-output-v3.md`
- Version = previous version + 1 (or 2 if first fix)
```
First standard output is `6-dev-output.md` (no version), first drift fix is `v2`. Why not `v1`?

**Impact:** Developers reading the files may miscount iterations. File naming is inconsistent (no version vs v2+).
**Category:** State Confusion
**Recommendation:** Either version all files (v1, v2, v3...) or clarify that no-version = v1 in documentation. Consistent naming reduces confusion.

### YELLOW FP-16: Review VERIFY_FIXES Mode Scope Restriction is Aspirational

### RED FP-17: Drift vs Bug Classification at QA Checkpoint Has No Automated Heuristics

**Location:** sf-review.md lines 1256-1267
**Context:** Distinguishing between drift (spec mismatch) and bugs (code errors) at QA checkpoint
**Friction:** The classification process described in sf-review.md requires semantic judgment. No automated signals are provided.
**Evidence:** From sf-review.md lines 1256-1267:
```markdown
### Drift vs Test Failure

| Situation | Type | Owner | Resolution |
|-----------|------|-------|------------|
| "Dev built logout but spec says password reset" | Drift | PM | Re-route to Dev |
| "Logout test fails: expected 200, got 401" | Bug | Review | Fix loop to Dev |
| "QA tests don't cover AC-03" | Drift | PM | Route to QA |
```
The examples require understanding intent vs implementation. No file-based or signal-based heuristics.

**Impact:** Misclassification routes to wrong agent (PM vs Review). Wastes iteration. This is the same issue as FP-09 from PM triage, but manifests in Review.
**Category:** Handoff Ambiguity
**Recommendation:** Add automated heuristics:
- Test file unchanged since QA wrote it + test fails -> likely CODE_ISSUE
- Test asserts different value than AC specifies -> likely TEST_DRIFT
- Implemented endpoint returns unexpected status -> likely BUG
- Implemented endpoint does wrong action -> likely DRIFT

### YELLOW FP-18: Parallel vs Sequential Fix Routing Depends on "Independence"

**Location:** sf-review.md lines 524-533
**Context:** Review decides whether to route Dev and QA fixes in parallel or sequentially
**Friction:** "Independence check" relies on Review's judgment: "Can be fixed without affecting other findings." No concrete criteria provided.
**Evidence:** From sf-review.md lines 524-533:
```markdown
**Independence check:**
- "Independent? Yes" = Can be fixed without affecting other findings
- "Independent? No" = Fix may impact other findings (e.g., refactor affects tests)

**Parallel routing decision:**
```
IF all_dev_issues_independent AND all_qa_issues_independent:
    route_parallel = true
ELSE:
    route_parallel = false
    note_dependencies = [list of dependent pairs]
```
```
How does Review determine if a naming change "affects" a test? Requires analysis.

**Impact:** Conservative routing (sequential) wastes time. Aggressive routing (parallel) causes merge conflicts.
**Category:** Under-specification
**Recommendation:** Add heuristics for independence:
- Same file touched by both -> NOT independent
- Test file + source file -> typically independent (parallel OK)
- Refactor finding + any other finding -> NOT independent
- Default to sequential if unsure (safe but slower)

**Location:** sf-dev-story.md lines 59-71

**Friction:** The TDD flow says "Run test - MUST fail" and "Run test - MUST pass" but:

### YELLOW FP-31: Story Acceptance Criteria Lack Detail for Parallel Development

**Validated:** 2026-02-05 during api-rate-limiting Wave 2 implementation

**Location:** sf-pm.md story generation, 5.5-epics.md story outlines
**Context:** Stories need concrete, detailed ACs for parallel developers to work independently
**Friction:** When multiple developers/agents work on parallel-safe stories, they need unambiguous acceptance criteria to avoid:
- Conflicting interface assumptions (e.g., function signatures, types)
- Inconsistent error handling patterns
- Overlapping file modifications
- Integration mismatches when stories merge

**Evidence:** From 5.5-epics.md story outline:
```markdown
**Acceptance Criteria:**
- [ ] Redis client created using ioredis
- [ ] Connection uses AUTH from environment variable
```

These ACs are high-level. For parallel development, they should specify:
- Exact function signatures: `getRedisClient(): Redis`
- Exact file paths: `src/lib/redis.ts`
- Exact env var names: `REDIS_URL`, `REDIS_TLS`
- Exact export names: `getRedisClient`, `closeRedisConnection`
- Interface contracts between stories

**Impact:** Parallel developers may implement incompatible interfaces. Story 1-3-sliding-window depends on 1-1-redis-client but doesn't know exact API shape until 1-1 completes.

**Category:** Under-specification (ACs too abstract for parallel work)

**Recommendation:**
1. **Interface-first ACs:** Stories that others depend on must specify exact interfaces
2. **Contract ACs:** Add AC like "Exports `getRedisClient(): Redis` function"
3. **Shared types file:** Create `src/types/rate-limit.ts` early with interfaces all stories use
4. **PM creates interface contracts:** Before Wave 1, PM defines shared interfaces used across stories

**Friction:** sprint-status.yaml tracks parallelization metadata that is never used:

**Evidence:** From sf-dev-story.md lines 160-163:

### RED FP-34: QA E2E/Integration Tests Written After Implementation Instead of Before

**Discovered:** 2026-02-05 during api-rate-limiting QA phase
**Observation:** QA invoked after all 8 stories complete, writing E2E tests post-facto instead of defining behavioral contract before Dev.

**Location:** sf-qa.md TDD_MODE, TEA test plan
**Context:** For TDD/BDD, behavioral tests (E2E, integration, API) should be written by QA BEFORE Dev implements
**Friction:**
1. TEA creates test plan with test specifications
2. PM routes to Dev without invoking QA first for TDD behavioral tests
3. Dev implements without having E2E tests as contract to code against
4. QA writes E2E tests after implementation - becomes "verification" not "specification"
5. Tests become coupled to implementation instead of defining expected behavior

**Evidence:** From api-rate-limiting workflow:
- TEA wrote test plan with E2E-01 through E2E-05 specifications
- PM routed directly to Dev for story implementation
- QA invoked only after all stories complete
- QA now writing E2E tests that describe what was built, not what should be built

**Impact:**
- E2E tests become documentation of implementation rather than specification
- Dev doesn't have behavioral contract to code against
- Missed bugs that TDD would catch (tests would fail during dev, not after)
- Tests may inadvertently encode implementation bugs as "expected behavior"

**Category:** Under-specification (TDD workflow not enforced)

**Recommendation:**
1. **TEA recommends flow:** If test plan says `recommended_flow: qa-first`, PM MUST route to QA before Dev
2. **QA TDD mode:** QA writes E2E/integration tests first, they SHOULD FAIL
3. **Dev implements to pass tests:** Dev's goal is making QA's tests pass
4. **Post-dev QA validates:** QA runs tests, verifies all pass

### RED FP-33: No Library/Module Discovery Before Implementation

**Discovered:** 2026-02-05 during api-rate-limiting feature implementation
**Observation:** Built sliding-window rate limiter from scratch when libraries like `rate-limiter-flexible` or `express-rate-limit` exist. No systematic search for existing solutions.

**Location:** sf-analyst.md (spec creation), sf-dev.md (implementation)
**Context:** Before implementing features, agents should check if existing libraries solve the problem
**Friction:**
1. Analyst creates spec without researching existing solutions
2. Dev implements from scratch without checking npm/pypi/crates for battle-tested libraries
3. Reinventing the wheel wastes time and introduces bugs that libraries already fixed
4. Custom code has maintenance burden that libraries handle

**Evidence:** From api-rate-limiting implementation:
- Built custom Lua script for sliding window algorithm
- Built custom Redis key management
- Libraries like `rate-limiter-flexible` already provide:
  - Multiple algorithm options (sliding window, token bucket, fixed window)
  - Redis integration with failover
  - Express middleware ready-to-use
  - Battle-tested in production

**Impact:**
- Wasted development time on solved problems
- Higher bug risk (custom code vs battle-tested library)
- Maintenance burden for code that could be delegated
- Missing features that libraries provide (clustering, monitoring, etc.)

**Category:** Under-specification (no library discovery step)

**Recommendation:**
1. **Analyst library search:** During spec creation, analyst spawns web search task to find existing libraries
2. **Build-vs-buy decision:** Analyst documents: "Existing solutions: X, Y, Z. Recommendation: use X because..."
3. **Dev library-first:** Dev checks for libraries before implementing. If AC can be met with library, use it.
4. **Custom code justification:** Only build custom when: (a) no library exists, (b) library doesn't meet requirements, (c) library has unacceptable tradeoffs (size, license, maintenance)
